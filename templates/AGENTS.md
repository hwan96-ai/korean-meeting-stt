# 회의록 작성 규칙

녹취 TXT를 AI(Claude Code, Codex 등)에 넘겨 회의록으로 쓸 때 아래 규칙과 해당 양식을 적용한다. 작성자가 실제로 쓰는 규칙에서 회사 이름과 저장 위치만 뺀 일반판이다. 자기 회사와 저장소에 맞게 고쳐 쓴다.

## 공통
- 회의 유형이 고객 미팅인지 주간회의인지 명확하지 않으면 확인한다.
- 녹취에 명시되지 않은 사실은 추측하지 않는다. 미확인 값은 `(미확인)`으로 표기한다. 일시, 장소, 참석자, 작성자 등 필요한 메타데이터가 없으면 사용자에게 확인을 요청한다.
- 회의 결론은 합의·결정 사항만 담는다. 논의만 되고 결정되지 않은 내용은 제외한다.
- 존댓말과 구어체를 문어체 개조식으로 바꾸고, 핵심 결정, 인사이트, 기술 세부사항, 사업 기회, 주요 인물과 일정을 **굵게** 강조한다.
- 녹취의 화자 구분은 내용 파악에 활용한다. 고객 미팅 본문에 발언자를 노출하지 않는다. 담당 업무를 구분해야 하는 경우 담당자를 명시한다.
- 표와 제목의 순서, 열 이름을 유지하되 실제 내용에 맞게 행과 글머리표 수를 조정한다. 빈 데이터로 행을 억지로 채우지 않는다.
- Notion 같은 DB 페이지로 출력할 때는 제목과 메타데이터를 DB 속성에 넣고 본문은 `1. 회의 결론`부터 시작한다. 파일로 출력할 때는 제목과 메타데이터 표를 포함한다. 속성 형식과 접근 권한을 확인하고 미확인 값을 형식에 맞지 않게 억지로 입력하지 않는다.

## 고객 미팅
- `고객-미팅-양식.md`를 따른다. 제목은 `[고객사] 미팅 회의록 (YYMMDD)`로 작성한다.
- 참석자는 `이름 직책 (회사)` 형식으로 줄바꿈해 적고 고객사 참석자를 먼저 배치한다. 모르는 이름, 직책, 회사는 추측하지 않는다.
- 핵심 논의사항은 주제별로 묶어 정제된 문장으로 요약한다.
- Next Step은 실제 해야 할 일만 기록한다. 담당자는 `이름 직책 (회사)`로 쓰고, 기한이나 조건은 내용 칸에 괄호로 넣는다. 기한 열을 만들지 않는다.
- 자사 소개와 현황은 최소화하고 포함할 때는 구분명에 `(참고)`를 붙여 뒤쪽 행에 배치한다.
- 사용자가 개발팀 검토·답변 요청을 지시하거나 회의에서 그런 요청이 명시된 경우 기본 세 섹션 뒤에 `4. 개발팀 답변 요청사항`을 추가한다. 확인 가능한 경우에만 중요도별로 묶고, 고객 요청과 확인할 사항을 정리한다. 개발팀 답변, 지원 여부, 공수와 일정은 근거 없이 만들어내지 않는다.
- 저장 대상 DB는 사용자의 요청과 접근 가능 여부를 확인한다.

## 주간회의
- `주간회의-양식.md`를 따른다. `1. 회의 결론`, `2. 담당자별 업무`, `3. 주요 일정` 순서를 유지한다.
- 담당자별 업무는 담당자 이름을 소제목으로 구분하고 각 업무와 후속 내용을 글머리표로 정리한다. 담당자가 불명확하면 `(미확인)`으로 표시한다.
- 주요 일정은 녹취에 확인된 날짜와 내용을 정리한다. 날짜나 주차가 없으면 추측하지 않고 확인한다.
- 저장을 요청받으면 대상 DB를 확인한다.
